Chapter 4 of 18

Learn what Firebase Hosting does

The last chapter left you with a request that needs a server. Several kinds of server can answer it. This chapter picks one for the campus page, and names two shapes the game can take later.

A computer that stays on

One option is a computer you rent and leave running. People call that a virtual machine or a VPS. Examples are an Amazon EC2 instance, a Google Compute Engine VM, an Azure virtual machine, a DigitalOcean droplet, or a campus lab machine that is never switched off. You install a web server on it. Apache HTTP Server and nginx are the usual ones. You point a domain name at that machine's IP address. The web server watches port 443 and sends the files when a browser asks.

When. You need a program of your own running all the time on that machine: a database you administer, a custom server you wrote, or files you want to arrange by hand over SSH.

Why it costs attention. You patch the operating system, renew the TLS certificate, notice when the disk fills, and start Apache or nginx again when it stops. The page is down while the machine is down. This campus page is a folder of files. It does not need a machine you babysit.

A host that only stores files

The other option is a service that stores your folder and answers HTTPS for you. You do not install Apache. You do not SSH into a box. Examples are Firebase Hosting, GitHub Pages, Netlify, Cloudflare Pages, and Amazon S3 with CloudFront. You upload the files, or you connect a Git repository and the service uploads them when you push. Many sites share their machines. Your job is the folder, not the operating system.

When. The site is HTML, CSS, JavaScript, and images, and someone else should keep the HTTPS answer running.

Why this book uses it. The campus page matches that description. The next chapter uploads the folder. The game you add later still runs in the browser, so the server's job stays "send these files."

Firebase Hosting, the option for this project

Firebase Hosting is the file host this book uses. You need a Google account, a Firebase project that you create, and the Firebase command-line tools. The project has an ID. After a deploy, the site is at https://YOUR_PROJECT_ID.web.app unless you attach a different domain later. Firebase presents the certificate. The address is https:// without you installing Apache or renewing a certificate by hand.

firebase.json names the folder. Yours will say the public folder is public. A deploy uploads the files in that folder: the HTML, the CSS, and the image. It does not upload the editor, and it does not upload a password. Do not put a service-account file or an API secret in public. Anything in that folder can be downloaded by anyone with the link.

When the setup command asks whether this is a single-page app, answer no. This site has a real index.html. A rewrite would send every address to one file and hide a missing page. Create your own Firebase project for this exercise. Do not deploy it into a project that already hosts a class site.

firebase.json · sits next to public, not inside it
{
  "hosting": {
    "public": "public",
    "ignore": ["firebase.json", "**/.*", "**/node_modules/**"]
  }
}

A single-page app, later

A single-page app, an SPA, is one HTML document. JavaScript shows and hides parts of it. Choosing Rules, Play, or Rounds does not ask the server for a second HTML file. The score stays in memory while the view changes.

Use it for this game, after the rounds exist. Rules, play, and recent rounds share one score. Separate HTML files would each load a fresh script, and the score would go back to zero.

Skip it for a book of chapters, a menu, or a news site. Each of those wants its own URL that still shows words if the script fails. This textbook is many HTML files for that reason.

The trade is real. The first download carries the whole app. One broken script breaks every view. A link to "just the rules" needs a plan, or it opens the same document. The later SPA chapter uses a hash, #play, so the browser swaps the view and the server still sees a request for index.html. That is why the rewrite stays off now. A missing image still returns 404.

A progressive web app, after that

A progressive web app, a PWA, is a site the browser can install. A manifest names the icon, the name, and the start address. A service worker is a script the browser keeps after the tab closes. It can answer later visits from a cache, including when the phone is offline.

Use it for the finished game. The rules and the score logic already live in the browser. After one visit on HTTPS, a player can open it from the home screen on the way to the event, with no signal.

Skip it while you are still editing every few minutes. The cache will keep showing the previous files until you change the cache name. Skip it for a page that must show a number from a server at the moment of the visit. A cached shell cannot invent today's score from a database you have not built.

A service worker that answers every path can also hide a missing file, the same way an SPA rewrite can. The later PWA chapter caches only the game's own files. The two chapters come after the game plays: first one page with three views, then an installable copy of that page.
